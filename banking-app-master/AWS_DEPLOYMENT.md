# AWS_DEPLOYMENT.md — Deploying the RCA Platform to AWS

This guide walks through deploying the full RCA platform to AWS using the Terraform configuration in `terraform/aws/`.

**Architecture:** VPC → public subnets → **three EC2 container instances (one per service)** → RDS MySQL. Each service runs in its own ECS task on its own dedicated EC2 host, pinned via ECS placement constraints. Credentials live in SSM Parameter Store (free tier). No CI/CD pipeline — images are built and pushed manually.

```
┌──────────────────────────────┐  ┌──────────────────────────────┐
│ EC2 host: monitored-app      │  │ EC2 host: ingestion-agent     │
│ default t3.small (2 GiB)     │  │ default t3.micro (1 GiB)      │
│   - banking-app (Spring Boot)│  │   - error-ingestion-agent     │
│   - dd-agent sidecar         │  │   - MODE=datadog_poll         │
│ Public port 8080             │  │ No inbound ports              │
└──────────────────────────────┘  └──────────────────────────────┘
┌──────────────────────────────┐  ┌──────────────────────────────┐
│ EC2 host: rca-agent          │  │ RDS MySQL (db.t3.micro)       │
│ default t3.small (2 GiB)     │  │ shared by all services        │
│   - FastAPI + Claude SDK     │  │                               │
│ Public port 8000             │  │                               │
└──────────────────────────────┘  └──────────────────────────────┘
```

**Why three hosts, not one?** Each service gets its own failure domain and right-sized RAM, and the **monitored app** is fully parameterized so you can swap banking-app for any other service without touching the ingestion-agent or rca-agent hosts (see "Swapping the Monitored Application" below).

**Memory budget** (ECS-optimized AMI eats ~1.1 GiB for OS + Docker + ECS agent):

| Host | Instance | Total RAM | Task memory | Headroom |
|---|---|---|---|---|
| monitored-app (Spring Boot + dd-agent) | `t3.small` | 2 GiB | 768 MiB | ~170 MiB |
| ingestion-agent (Python poller) | `t3.micro` | 1 GiB | 256 MiB | ~200 MiB |
| rca-agent (Python FastAPI + Claude SDK) | `t3.small` | 2 GiB | 512 MiB | ~430 MiB |

> **Note on ingestion mode:** the AWS deployment uses `MODE=datadog_poll` — the ingestion agent pulls logs from the Datadog Logs API, so it does **not** need to share a log file volume with the monitored-app container. That's what makes the per-host split safe. Don't switch back to `MODE=db` (file tailing) on this topology — there's no shared volume across EC2 instances. The local docker-compose stack remains single-host and supports both modes.

## Prerequisites

- AWS CLI configured (`aws configure`) with permissions for ECS, EC2, ECR, RDS, VPC, IAM, SSM
- Terraform >= 1.6
- Docker (for building and pushing images)
- Real Datadog credentials (DD_API_KEY, DD_APP_KEY)
- Anthropic API key, GitHub PAT, Google Gemini API key

## Step 1 — Terraform Init & Apply

```bash
cd terraform/aws

# Create your tfvars file
cp terraform.tfvars.example terraform.tfvars
# Edit terraform.tfvars — at minimum set aws_region, environment, github_org, dd_site.
# To swap the monitored app, edit the `monitored_app = { ... }` block (see "Swapping" below).

terraform init
terraform plan -var-file=terraform.tfvars
terraform apply -var-file=terraform.tfvars
```

This creates (in order):
1. VPC, public subnets, **four security groups** (one per host + one for RDS)
2. RDS MySQL instance (takes ~5 minutes) — **password auto-generated by Terraform**
3. ECR repositories (4 repos — monitored-app name follows `var.monitored_app.image_repo_name`)
4. SSM Parameter Store parameters:
   - `rds-password` and `database-url` — **auto-populated by Terraform** (no manual step)
   - `anthropic-api-key`, `github-pat`, `gemini-api-key`, `dd-api-key`, `dd-app-key` — placeholder values, overwrite in Step 2
5. ECS cluster, three task definitions, three services
6. **Three EC2 container instances**, each registered with the cluster under a `module` attribute (`monitored-app`, `ingestion-agent`, `rca-agent`). ECS placement constraints pin each service to its matching host.

Note the outputs — you'll need them in the next steps:
```bash
terraform output ecs_cluster_name
terraform output rds_endpoint                # for reference / direct DB access
terraform output ecr_monitored_app_uri       # for docker push commands
terraform output monitored_app_public_ip     # for the monitored-app health check
terraform output rca_agent_public_ip         # for the rca-agent health check
terraform output ingestion_agent_public_ip   # for SSH/debug only
terraform output ssm_parameter_names         # shows all parameter paths
```

## Step 2 — Populate SSM Parameter Store

After apply, five external-service credentials need to be set. The database password and full `DATABASE_URL` are **auto-populated by Terraform** — you do not need to set those manually.

SSM Parameter Store standard parameters are **free** — no per-secret monthly charge unlike Secrets Manager. Values are encrypted at rest using the AWS-managed KMS key (`aws/ssm`) and injected into ECS containers at task start — never stored in images or task-definition plaintext.

```bash
# Helper function
function put_param() {
  aws ssm put-parameter \
    --name "$1" \
    --value "$2" \
    --type SecureString \
    --overwrite
}

put_param "/banking-app/production/anthropic-api-key" "sk-ant-..."
put_param "/banking-app/production/github-pat"         "ghp_..."
put_param "/banking-app/production/gemini-api-key"     "AIza..."
put_param "/banking-app/production/dd-api-key"         "<your-dd-api-key>"
put_param "/banking-app/production/dd-app-key"         "<your-dd-app-key>"
# rds-password and database-url are managed by Terraform — do NOT overwrite them.
```

> **Verify all parameters are set:**
> ```bash
> aws ssm get-parameters-by-path \
>   --path "/banking-app/production" \
>   --with-decryption \
>   --query "Parameters[*].{Name:Name,Value:Value}" \
>   --output table
> ```
> The `rds-password` and `database-url` rows should already have real values from Terraform.
> The other five rows should show the credentials you just set (not `REPLACE_ME`).

## Step 3 — Build and Push Images to ECR

```bash
# Authenticate Docker with ECR
AWS_ACCOUNT=$(aws sts get-caller-identity --query Account --output text)
AWS_REGION=us-east-1
ECR_BASE="${AWS_ACCOUNT}.dkr.ecr.${AWS_REGION}.amazonaws.com"

aws ecr get-login-password --region ${AWS_REGION} \
  | docker login --username AWS --password-stdin ${ECR_BASE}

# From the banking-app-master root:
cd banking-app-master

# 1. Monitored app (banking-app by default — repo name follows monitored_app.image_repo_name)
docker build -t banking-app .
docker tag banking-app:latest ${ECR_BASE}/banking-app:latest
docker push ${ECR_BASE}/banking-app:latest

# 2. error-ingestion-agent (context = repo root so projects.yaml can be baked in)
docker build -f error-ingestion-agent/Dockerfile -t ingestion-agent .
docker tag ingestion-agent:latest ${ECR_BASE}/banking-app/ingestion-agent:latest
docker push ${ECR_BASE}/banking-app/ingestion-agent:latest

# 3. rca-agent
docker build -t rca-agent ./rca-agent
docker tag rca-agent:latest ${ECR_BASE}/banking-app/rca-agent:latest
docker push ${ECR_BASE}/banking-app/rca-agent:latest

# 4. Datadog agent sidecar (custom image with monitored-app log config baked in)
docker build -t dd-agent ./datadog
docker tag dd-agent:latest ${ECR_BASE}/banking-app/dd-agent:latest
docker push ${ECR_BASE}/banking-app/dd-agent:latest
```

> **Note:** After every code change, rebuild the affected image and push to ECR, then force a new ECS deployment:
> ```bash
> aws ecs update-service --cluster banking-app-cluster \
>   --service <service-name> --force-new-deployment
> ```
> The service-name matches `var.monitored_app.service_name` (default `banking-app`), `ingestion-agent`, or `rca-agent`.

## Step 4 — Run Alembic Migrations

The `rca-agent` Dockerfile already runs `alembic upgrade head` in its CMD. On first deploy, ECS will run migrations automatically when the task starts.

If you need to run migrations manually (e.g., after a schema change):

```bash
# Connect to the rca-agent task via ECS Exec
aws ecs execute-command \
  --cluster banking-app-cluster \
  --task <task-id> \
  --container rca-agent \
  --interactive \
  --command "alembic upgrade head"
```

## Step 5 — Seed service_repo_map

The RCA agent needs to know which GitHub repo to search for each service. Run the seed script once after initial deploy:

```bash
# Pull the full DATABASE_URL from SSM (Terraform stored it there — password included)
DB_URL=$(aws ssm get-parameter \
  --name "/banking-app/production/database-url" \
  --with-decryption \
  --query "Parameter.Value" \
  --output text)

python demo-repos/demo_seed_data.py \
  --org oscorpAI \
  --db-url "${DB_URL}"
```

This inserts `banking-app`, `payment-service`, and `order-service` into `service_repo_map`.

## Step 6 — Verify the Deployment

Each service lives on its own host, so each check targets a different IP.

```bash
# Pull the three per-host IPs created by Terraform.
MONITORED_IP=$(terraform -chdir=terraform/aws output -raw monitored_app_public_ip)
RCA_IP=$(terraform -chdir=terraform/aws output -raw rca_agent_public_ip)

# 1. Check monitored-app health (port from var.monitored_app.port — default 8080)
curl http://${MONITORED_IP}:8080/actuator/health

# 2. Check rca-agent health
curl http://${RCA_IP}:8000/health

# 3. List available chaos scenarios
curl http://${RCA_IP}:8000/chaos/scenarios | python3 -m json.tool

# 4. Trigger a NullPointerException on the monitored-app
curl -X POST http://${MONITORED_IP}:8080/chaos/null-pointer

# 5. Wait 30-60 seconds, then check for pending RCA reports
curl http://${RCA_IP}:8000/demo
# Open in browser — the report should appear automatically
```

The ingestion-agent host has no inbound ports — its task polls Datadog outward and writes to RDS. To inspect it, use ECS Exec via the AWS console or `aws ecs execute-command`.

## Swapping the Monitored Application

The platform is application-agnostic: only the monitored-app host knows or cares which app it's running. To replace banking-app with a different application:

1. **Edit `terraform.tfvars`** — change the `monitored_app = { ... }` block. The fields:

   | Field | Purpose |
   |---|---|
   | `service_name` | Label used in env vars, ECS service name, DD tags, log group name |
   | `image_repo_name` | ECR repository name. Terraform creates/manages this repo. |
   | `image_tag` | ECR image tag |
   | `port` | Public TCP port the app serves. The monitored-app SG auto-opens this. |
   | `task_cpu` / `task_memory` | ECS task sizing (memory in MiB) |
   | `instance_type` | EC2 instance type for the monitored-app host. Right-size to `task_memory + ~1.1 GiB OS overhead`. |
   | `needs_dd_sidecar` | true to colocate the Datadog agent sidecar; false for apps that ship logs another way |
   | `extra_env` | Arbitrary env vars for the app container |

2. **Build and push the new image to ECR.** The repo URI comes from `terraform output ecr_monitored_app_uri`.

3. **`terraform apply`** — this re-shapes the monitored-app task definition, security group, and (if `instance_type` changed) replaces the EC2 host. The ingestion-agent and rca-agent hosts are untouched.

4. **Seed the new service in `service_repo_map`** so the RCA agent knows which GitHub repo to analyse.

No code changes anywhere in the platform. The example block in `terraform.tfvars.example` shows banking-app's defaults plus a commented "order-app" swap example.

## Tearing Down

```bash
cd terraform/aws

# Stop ECS services first (avoids dependency issues during destroy)
aws ecs update-service --cluster banking-app-cluster --service banking-app      --desired-count 0
aws ecs update-service --cluster banking-app-cluster --service ingestion-agent  --desired-count 0
aws ecs update-service --cluster banking-app-cluster --service rca-agent        --desired-count 0

# Destroy all infrastructure (3 EC2 instances + RDS + VPC + ECR + IAM + SSM)
terraform destroy -var-file=terraform.tfvars
```

> **SSM parameters** are deleted immediately by `terraform destroy` — no recovery window.
> **ECR images** must be deleted manually before the repositories can be destroyed, or set `force_delete = true` in the ECR resource.
> ```bash
> # Quickly empty all four ECR repos before destroy
> for repo in banking-app banking-app/ingestion-agent banking-app/rca-agent banking-app/dd-agent; do
>   aws ecr list-images --repository-name "$repo" \
>     --query 'imageIds[*]' --output json \
>   | xargs -I{} aws ecr batch-delete-image --repository-name "$repo" --image-ids {}
> done
> ```

## CI/CD (Not Implemented)

The project does not have a CI/CD pipeline. To deploy a code change:

1. Build the updated image locally
2. Push to ECR with a new tag (or `latest`)
3. Run `aws ecs update-service ... --force-new-deployment` against the affected service

For a production setup, a GitHub Actions workflow would automate steps 1-3 on push to `main`. This is tracked as a future improvement.
